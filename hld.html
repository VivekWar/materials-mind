2. Core Infrastructure Components

The Edge Layer

React Frontend: Renders technical data via KaTeX. Connects to the backend using credentials: 'include' to pass secure cookies automatically.

Load Balancer: Distributes user traffic across multiple Go instances. Scales automatically based on concurrent open SSE (Server-Sent Event) connections.

The Application Layer

Go / Gin API: Strictly stateless application. Implements a "Fail-Fast" boot sequence. Uses Go goroutines and sync.WaitGroup to execute API calls to LLMs and databases concurrently, cutting latency by 50%.

The 3-Tier Cache (Redis Stack)

  • Semantic Cache: Uses Redis Vector Search to intercept duplicate queries (e.g., "drone frame" vs "frame for drone") and returns cached LLM text, saving API costs.
  • Object Cache: Maps Postgres IDs to complete JSON objects for 1ms retrieval of material parameters.
  • Sliding Window: Keeps active chat histories in fast memory, syncing to Postgres asynchronously.

The Data Layer (PostgreSQL + pgvector)

Primary Node: Handles user authentication states, conversation history backups, and ETL data loading.

Read Replicas: Handles all HNSW vector similarity searches (<=> operator). Because vector math is CPU-intensive, isolating it to replicas prevents database locking during high user traffic.

3. Request Lifecycle (The Hybrid RAG Flow)

  1. Authentication: Request hits the Go API. Middleware verifies the HttpOnly JWT cookie and checks the IP against the Redis token-bucket rate limiter.
  2. Short-Circuit Check: The query is embedded and checked against the Redis Semantic Cache. If a >98% match exists, the cached response is returned immediately.
  3. The Fork in the Road: The request enters concurrent Goroutines. Path A extracts hard mathematical constraints (e.g., yield > 500). Path B generates the semantic vector.
  4. Hybrid Merge: The system builds a dynamic SQL query combining the exact WHERE clauses from Path A with the ORDER BY vector from Path B.
  5. Hydration: Top IDs are returned from Postgres. The Go server fetches the full material profiles from the Redis Object cache.
  6. Explainable AI: The hydrated context is passed to Gemini 2.5 Flash. The engineering report is streamed word-by-word back to the user via Server-Sent Events (SSE).

5. How To Improve Output Extraction Quality

"Output extraction" can be made much stronger by making model outputs structured, validated, and observable.

A. Structured Extraction Contract

  • Force LLM output to strict JSON schema (fields like constraints, units, material_candidates, confidence).
  • Reject free-form responses for extraction step; retry automatically on schema failure.
  • Normalize units (MPa, GPa, g/cm3) before SQL build to avoid wrong filtering.

B. Better Retrieval + Ranking

  • Use hybrid retrieval score: alpha * vector_score + beta * constraint_match + gamma * recency.
  • Add reranker stage for top-20 candidates before final context packing.
  • Store query-result feedback and continuously tune alpha/beta/gamma.

C. Grounded Report Generation

  • Prompt template should require each recommendation to cite source material IDs.
  • Split output into fixed sections: assumptions, selection logic, tradeoffs, final recommendation.
  • Flag low-confidence fields and explicitly ask user for missing constraints.

D. Interview-Ready Metrics

  • Extraction validity: % outputs passing JSON schema.
  • Grounding rate: % claims backed by retrieved records.
  • P95 latency: end-to-end response latency with and without cache hit.
  • User correction rate: how often users must rephrase/refine prompts.
